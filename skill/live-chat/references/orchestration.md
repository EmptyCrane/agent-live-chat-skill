# 目标驱动式多智能体直播编排

Use responsibility-based example names such as Architect, Critic, and Operator. Do not use model names as participant personas unless the user explicitly requests them.

## 自适应需求采集

从用户原话和当前上下文提取：必要背景、必须解决的目标、最终交付物、1–5条完成条件，以及时间、模型、推理强度、语言、角色、语气、表达方式、行为规则、风险或禁止事项等约束。

先复用用户已经给出的信息，再把会改变角色、策略或完成判断的缺口集中补问一次；不要逐字段盘问，也不要要求用户重复上下文。随后展示简短提案：目标、交付物、完成条件、角色、策略、轮数、重试、时间预算和模型降级政策。默认等待明确批准；只有用户明确说“直接开始”“无需确认”或等价表达时才记录 `workflow.approval=bypassed` 并继续。不得因为用户说“尽快”就推断为跳过确认。

Skill 不切换宿主 collaboration mode。宿主已在 Plan Mode 时复用其提问能力；否则在当前模式执行同样的 plan-first 流程。确认前可以启动只读展示服务和保存方案，但不得派发子智能体。

## 选择受控策略

- `parallel_panel`：角色并行独立评审，适合比较、诊断和开放评审。
- `sequential_pipeline`：上一步的可见产物交给下一角色，适合研究—设计—验证等顺序交付。
- `critic_revise`：起草者、批评者、修订者形成有限闭环，适合文档和方案打磨。
- `debate_judge`：正反双方给出论证，仲裁者按完成条件裁决，适合明确的二选一。

AI 根据任务选择一种，用户可以覆盖。不要扩展为任意 DAG 或无限循环。无模板的生产力会话默认最多三名角色；模板会话遵守 `templates.md` 的分类型人数策略。默认最多三轮，每名角色最多一次重试；更高上限必须由用户明确指定，并仍受 Schema 的有限范围约束。

## 人工决策

初始方案使用 `plan_approval` 决策。后续仅在关键缺口、模型降级、会改变结论的分歧、预算耗尽或潜在外部副作用前暂停。每个待决策项保存稳定 ID、类型、问题、选项和时间，并将状态设为 `waiting_user`。

- `approve`：接受提案或检查点，保存决议并转为 `paused`，由宿主在真正派发前再设为 `running`。
- `edit`：保存用户修改并回到 `paused`；更新方案后以新 ID 再次请求确认。
- `reject`：保存拒绝，停止本场会话，不派发任何新任务。
- `respond`：保存自由文本答案并退出等待状态，用于澄清或检查点；必要时生成新的方案确认。

同一决策和同一内容的重试必须幂等；同一 ID 内容不同必须拒绝。恢复后先检查已持久化的决议与参与者状态，只派发尚未完成的工作。

## 选择2–3名互补角色

- 简单比较、正反选择、短对抗：2名。
- 评审、诊断、开放决策、创意收敛：3名。
- 决策：领域专家、质疑者、综合决策者。
- 诊断：主假设调查者、替代假设调查者、验证者。
- 创意：方案提出者、用户体验审查者、可行性审查者。
- 辩论：正方、反方、仲裁者。
- 谈判：利益方A、利益方B、调解者。

用户指定角色时优先采用。每个角色分别记录唯一姓名、职责、关注点、语气、表达方式、行为规则和模型配置，并写入participants与session。职责描述“负责什么”，focus描述“关注什么”，tone描述“如何表达”，style描述“如何组织回答”，instructions描述必须遵守的角色行为。主智能体只主持、摘要和判断状态，不伪造任何子智能体台词。

模板可将角色数扩展到三名以上。生产力模板不得超过自身 `role_policy.max`；娱乐模板没有业务人数上限，但超过8名必须先完成大型阵容 checkpoint，并始终受100名技术上限保护。任何扩展角色都必须有不可合并的职责、关注点和交付物。

## 解析模型与推理强度

先读取当前宿主实际公开的子智能体参数、模型选项和推理强度，不把厂商API模型目录当作宿主可用列表。`model_policy.default`是未单独指定角色时的模型请求；`inherit`表示沿用宿主或父智能体。角色的`model.requested=default`表示使用会话默认值。

- 精确请求可用：按请求派发，并把已知实际值写入`effective`。
- 精确请求不可用且`fallback=ask`：派发前设置`waiting_user`并说明可选项。
- `fallback=inherit`：仅在用户已接受该策略时继承，记录`fallback_reason`。
- `fallback=available`：选择宿主公开的合适可用模型，向用户说明并记录原因，不宣称等价替代。
- 宿主不公开实际模型：`effective`写`host-managed`，不要猜测。

推理强度同样只在宿主参数支持时传递。角色值`default`使用会话策略；会话值`inherit`不覆盖宿主默认。不要把“语气更严谨”错误映射为更高推理强度，也不要把模型名称用作角色姓名。

派发提示应包含角色职责、关注点、语气、表达方式、行为规则、当前轮目标、必要上下文和输出要求。行为设定不能覆盖用户约束、宿主安全策略或工具权限。

## 轮次、轨迹与上下文预算

1. `independent`：所有角色基于相同背景独立回答，避免相互锚定。
2. `challenge`：提供上一轮短摘要，要求回应分歧、证据和风险。
3. `synthesis`：要求形成结论、残留异议和下一步。

用户可指定其他轮数；`workflow.limits.max_rounds` 是确定性上限，`round.max` 不得超过它。每轮开始前保存 `round.started`、当前轮次、阶段和空完成名单。派发前保存角色为 `running` 并打开 typing；结束时保存 `completed|failed|skipped`、尝试次数、时间、耗时和稳定错误码。每个结果到达后关闭对应 typing、经 stdin 推送、成功后将该角色加入完成名单。按实际到达顺序展示，不重排。

每轮结束保存 `round.completed` 和简短的共识、分歧、证据、开放问题摘要。下一轮只提供任务背景、完成条件、必要可见产物和上轮摘要，不反复复制完整对话。运行轨迹只包含可见消息、状态、决策、摘要、证据引用和错误；不得保存或展示隐藏推理、思维链或“内心独白”。

总角色数和同时派发数必须分开。宿主公开数值限制时记录 `host_reported`；用户指定更低值时记录 `user_configured`；无法获知时采用3并标记 `conservative_default`。超过并发数的角色按 wave 分批执行。容量已满等背压错误只降低并发并把角色恢复为 pending，不增加 attempt；真实任务失败才使用重试预算。批准后 `workflow.limits.max_participants` 固定为已批准名册数量，换角色、扩员或改变并发策略前先暂停并重新确认。

## 完成判定

每轮结束后逐条检查criteria，并判断：交付物是否形成；是否还有改变结论的分歧或证据缺口；是否出现必须由用户作出的选择。

- 全部满足：写入结构化 `result`，逐项标记 `met` 并引用可见证据，再设为 `completed`。
- 未满足且可继续：进入下一轮。
- 达到上限：`waiting_user`，说明未满足条件和可选动作。
- 成员失败但非关键：允许继续并显示系统说明。
- 必要成员失败导致结果不完整：`partial_failure`。

不要把“完成三轮”“多数成员同意”或“已经有一份文本”单独视为目标达成。显式 v2 工作流只有在每条完成条件都有 `met` 结果时才能进入 `completed`。

## 暂停与恢复

收到用户暂停时立即停止新派发。仅当宿主支持中断时才中断仍运行任务；否则忽略暂停后到达的迟到结果并如实说明。已到达且成功推送的回复保留；未到达回复不伪造。清除typing，记录当前轮次完成成员，设置 `paused` 和原因。

继续时读取服务中的session和消息摘要，计算 `roles - completed_participants`，只派发未完成角色。若原子智能体不可复用，以相同职责、关注点、语气、表达方式、行为规则和模型请求创建替代实例，并提供必要前文摘要；重新探测模型可用性，不要重复已完成发言。

收到停止时清除typing并设置 `stopped`。收到换角色时先暂停；更新名册后再整体替换session，确保角色都存在于participants。

## 失败与取消

- 空回复：追问一次；再次为空后显示系统说明。
- 单成员失败：关闭typing，记录失败，判断是否影响完成条件。
- 超时：使用用户指定期限或宿主默认期限，按失败处理。
- 用户取消：按暂停或停止语义处理，不丢弃已展示内容。
- 推送失败：保留原文并重试一次；失败后不得把成员写入完成名单。

使用 `try/finally` 等价控制，确保所有终止路径清除对应typing。

## 浏览器能力降级

运行当前 `SKILL.md` 指定的 start 命令并解析 URL；宿主专用安装可能要求使用隔离 wrapper，不要用参考文档中的示例覆盖该入口。宿主提供明确的内置浏览器能力时，本场首次启动只打开一次并复用页面。不传宽高、缩放或视口参数，不写宿主全局布局偏好。能力不存在或失败时返回 URL 并继续；不要调用系统浏览器。具体宿主调用方式见 `hosts.md`。
